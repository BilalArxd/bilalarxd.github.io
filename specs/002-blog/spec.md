# Feature Specification: Blog — Paginated List & Post Detail Pages

**Spec ID**: 002-blog
**Created**: 2026-07-28
**Status**: Clarified
**Stack**: TypeScript / JavaScript, React, Next.js, Tailwind CSS, npm, GitHub Actions

---

## 1. Problem Statement

Bilal wants a simple blog section on his portfolio site (`bilalarxd.github.io`) so he can publish written posts alongside his existing profile/experience/projects content — including posts generated directly by Claude as summaries of completed work. The site is statically exported (`output: 'export'`) with no backend or database, so the blog must be built entirely from content known at build time (local HTML files with a small front-matter header) — no CMS, no server-rendered routes. GitHub Pages serves static files only, so post discovery happens at build time; every push to `main` already auto-triggers a build + deploy (spec `001-portfolio-hello-world`), so publishing a post is: write one file, `git push`, live in ~2 minutes — no manifest/index to hand-edit. The increment covers exactly two pages: a blog index that lists all posts with pagination, and a blog detail page that renders a single post's full content. No comments, tags/categories, search, or authoring UI are in scope.

## 2. User Scenarios & Acceptance Criteria

### Story 1 — Browse paginated post list (Priority: P1)

As a visitor, I want to see a list of blog posts (title, date, short excerpt) with pagination, so I can browse Bilal's writing without an overwhelming single page.

**Why P1**: The list is the entry point to all blog content — without it, individual posts are undiscoverable.

**Acceptance Scenarios**:
1. **Given** more posts exist than fit on one page, **When** a visitor loads `/blog`, **Then** the first page shows the newest N posts (sorted by publish date, descending) with title, date, and a short excerpt for each.
2. **Given** the visitor is on `/blog`, **When** they navigate to page 2 (`/blog/page/2`), **Then** the next page of posts is shown, and pagination controls indicate current page and total pages.
3. **Given** the total number of posts is less than or equal to one page size, **When** a visitor loads `/blog`, **Then** all posts are shown and no pagination controls are rendered.
4. **Given** a visitor requests a pagination page number beyond the last valid page, **When** the route is built, **Then** that page is not generated (404 on that path) — only valid page numbers exist as static routes.

### Story 2 — Read a single post (Priority: P1)

As a visitor, I want to click a post from the list and read its full content on its own page, so I can consume one article at a time with a shareable URL.

**Why P1**: This is the actual content-delivery mechanism — the list alone has no value without a working detail view.

**Acceptance Scenarios**:
1. **Given** a post exists with slug `my-post`, **When** a visitor loads `/blog/my-post`, **Then** the page renders the post's title, publish date, and full body content (the post's own HTML — headings, paragraphs, lists, code blocks, links, images).
2. **Given** a visitor is reading a post, **When** they want to go back to browsing, **Then** a link back to the blog list (or the list page they came from) is visible on the page.
3. **Given** a slug with no matching post, **When** that path is requested, **Then** it is not a statically generated route (404), since all valid post routes are known at build time.

### Story 3 — Simple content authoring, including by Claude (Priority: P2)

As Bilal, I want to add a new post by adding a single static HTML file with a small front-matter header, so I can publish without touching page/layout code — and so that Claude can generate a post directly (e.g. a summary of work just completed) simply by writing that one file and pushing it.

**Why P2**: Not required for the pages to function, but needed for the feature to be usable ("keep it simple" implies low-friction authoring, not a CMS) — and this is the explicit authoring workflow requested: write one file, push, no manual list/index editing.

**Acceptance Scenarios**:
1. **Given** a new HTML file is added to the posts content directory with required front-matter (`title`, `date`, `slug` or filename-derived slug, `excerpt`) followed by the post's HTML body, **When** the site rebuilds (automatically, on push to `main`, per the existing CI/CD from spec `001`), **Then** the post appears in the list (in correct date order) and its detail page is generated — no manifest/index to hand-edit, whether the file was written by Bilal or generated by Claude.
2. **Given** a post is missing required front-matter fields, **When** the site is built, **Then** the build fails with a clear error identifying the offending file, rather than silently rendering a broken page.
3. **Given** the post content format, **When** a post file is authored, **Then** it is a `.html` file with a YAML front-matter header (`---`-delimited) followed by plain HTML body markup — no Markdown rendering step is applied to the body (decided in `clarifications.md` Q6, superseding the earlier Markdown-only decision in Q5).
4. **Given** GitHub Pages cannot execute server code at request time, **When** a new post file is pushed, **Then** "no rebuild" is understood as "no manual rebuild step for Bilal/Claude" — the existing push-triggered CI build (spec `001`) still runs automatically and is what makes the post live, typically within ~2 minutes.

## 3. Technical Design

### 3.1 Tech Stack Context

From `.apex/stack.json`:
- **Language**: TypeScript
- **Framework**: Next.js (App Router) with React, statically exported (`output: 'export'`)
- **Database**: None — posts are local HTML files (with a YAML front-matter header) read at build time, no runtime data source
- **Styling**: Tailwind CSS, consistent with existing site sections
- **Package manager**: npm
- **Infrastructure**: GitHub Actions → GitHub Pages (existing pipeline from spec `001-portfolio-hello-world`, unchanged)
- **Version constraints**: Only static-export-compatible Next.js features — `generateStaticParams` for all dynamic routes (post slugs and pagination pages), no API routes, no ISR/on-demand revalidation, no `next/image` optimization API.

### 3.2 Architecture Fit

- New content source: `content/blog/*.html`, one file per post — a YAML front-matter header (`---`-delimited, parsed with `gray-matter`) followed by the post's body written directly as HTML (no Markdown/MDX transformation step; decided in `clarifications.md` Q6).
- New routes under the existing App Router structure, mirroring the pattern of `app/experience/page.tsx` and `app/projects/page.tsx`:
  - `app/blog/page.tsx` — page 1 of the list (`/blog`).
  - `app/blog/page/[page]/page.tsx` — subsequent list pages (`/blog/page/2`, `/blog/page/3`, …), each with `generateStaticParams` enumerating valid page numbers (2..N; page 1 stays at `/blog` and is not duplicated under `/page/1`).
  - `app/blog/[slug]/page.tsx` — post detail page, `generateStaticParams` enumerating all post slugs.
- New lib module `app/lib/posts.ts` (mirroring `app/lib/projects.ts` style) — reads and parses all Markdown files once, exposes `getAllPosts()`, `getPostBySlug(slug)`, and a paginate helper; both list routes and detail route consume this module so post loading logic lives in one place.
- Post list items reuse existing card-style presentation conventions from `ProjectCard.tsx` where reasonable, but as a new `BlogPostCard.tsx` component (posts have different fields — date/excerpt vs. tech stack).
- Front-matter parsing: `gray-matter` extracts `title`/`date`/`slug`/`excerpt` from the `---` header; the remainder of the file is the post's raw HTML body, rendered as-is (via `dangerouslySetInnerHTML` in a Server Component, safe since content is self-authored) inside a Tailwind `prose` wrapper for typography (decided in `clarifications.md` Q6, superseding Q2's Markdown pipeline — no syntax highlighting is applied either way in this increment, per Q2's original rationale).
- `app/components/Nav.tsx` gets a "Blog" link alongside the existing Experience/Projects links, so the section is discoverable from anywhere on the site (decided in `clarifications.md` Q3).
- Post images (where present) live under `public/blog/<slug>/...` and are referenced with absolute paths, rendered as plain `<img>` — consistent with the existing `images: { unoptimized: true }` static-export setup from spec `001-portfolio-hello-world` (decided in `clarifications.md` Q4).

### 3.3 Data Model Changes

New content type (file-based, not a database):
- **Post** (one HTML file per post in `content/blog/`):
  - `title: string` (required)
  - `date: string` (ISO date, required) — used for sort order
  - `slug: string` (required; derived from filename if omitted)
  - `excerpt: string` (required) — shown in list view
  - `body: string` (required) — raw HTML content, everything after the `---` front-matter block, rendered as-is (no Markdown transformation); may include `<img>` tags referencing `public/blog/<slug>/`

Seed content: 2–3 posts included with this feature so list/pagination/detail behavior is demonstrable immediately; at least one seed post includes an image to exercise the image-rendering path (decided in `clarifications.md` Q4).

### 3.4 API Design

None — no API routes; all content resolved at build time via `generateStaticParams` and file-system reads in Server Components.

### 3.5 Component / Module Design

- `app/lib/posts.ts` — front-matter parsing (`gray-matter`) over `content/blog/*.html`, sorting (newest first), pagination math. No Markdown rendering step — the front-matter body is used as raw HTML directly. Exports `PAGE_SIZE = 10`, `getAllPosts()`, `getPostBySlug()`, `getPostsPage(pageNumber)`, `getTotalPages()`.
- `app/blog/page.tsx` — renders list page 1 using `getPostsPage(1)`.
- `app/blog/page/[page]/page.tsx` — renders list page N; `generateStaticParams` returns `[{ page: '2' }, { page: '3' }, ...]` for all valid pages beyond 1.
- `app/blog/[slug]/page.tsx` — renders single post; `generateStaticParams` returns all slugs from `getAllPosts()`; post body rendered via `dangerouslySetInnerHTML` inside a Tailwind `prose` container.
- `app/components/BlogPostCard.tsx` — title, date, excerpt, link to detail page; used by both list pages.
- `app/components/Pagination.tsx` — prev/next + page-number links, current-page indicator, only rendered when total pages > 1.
- `app/components/Nav.tsx` — updated to add a "Blog" link.
- `content/blog/*.html` — post source files (front-matter header + HTML body); 2–3 seed posts included, at least one with an image under `public/blog/<slug>/`.

## 4. Non-Functional Requirements

| Requirement | Target | Measurement |
|------------|--------|-------------|
| Static compatibility | 100% of blog routes (list pages + post pages) statically generated at build time, zero server runtime dependency | `next build` export succeeds without dynamic-route warnings |
| Build reproducibility | Adding/editing an HTML post file and pushing (CI rebuild, no manual step) regenerates correct list order and routes | Manual verification: add seed post, push, confirm the auto-deployed site shows `/blog` and its route updated |
| Content validation | Missing required front-matter fields fail the build with a clear, file-identifying error | Manual test: post with missing field fails `next build` |
| Accessibility baseline | List and detail pages use semantic HTML (single `h1` per page, ordered reading structure, accessible pagination links) | Manual review |

## 5. Out of Scope

- Comments, reactions, or any visitor interaction.
- Tags, categories, or search/filtering.
- RSS feed, sitemap entries specific to blog (may be added in a later increment).
- Any CMS, admin UI, or in-browser authoring — posts are authored as local HTML files only (by Bilal directly, or by Claude generating the `.html` file on his behalf — both are the same workflow from the site's perspective).
- Markdown as a content format — reversed by `clarifications.md` Q6; posts are raw HTML files with a YAML front-matter header, no Markdown/MDX rendering pipeline.
- Literal runtime (no-rebuild) content discovery — not possible on GitHub Pages static hosting (no server at request time); "no manual step" is satisfied via the existing push-triggered CI build from spec `001` instead (decided in `clarifications.md` Q6).
- Draft/unpublished post workflow (all files in the content directory are treated as published).
- Reading time estimates, related-posts, or social share buttons.
- Syntax highlighting for code blocks (renders as plain monospace `<pre><code>` for now — deferred per `clarifications.md` Q2, not a gap).

## 6. Dependencies & Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Front-matter parsing adds server-only APIs incompatible with static export | Low | Medium | Use build-time-only parsing (Node `fs` + `gray-matter`) inside Server Components/`generateStaticParams`, never client-side |
| Pagination route numbering drifts from actual post count as posts are added/removed | Low | Low | Compute total pages from `getAllPosts().length` at build time via `getTotalPages()`, never hard-code page counts |
| Large post bodies (images, code blocks) breaking styling consistency with rest of site | Medium | Low | Scope a minimal typographic style (e.g. Tailwind `prose` classes) for the rendered HTML body |
| Raw HTML body injected via `dangerouslySetInnerHTML` could render broken/malformed markup if a post file is hand-edited carelessly | Low | Low | Content is self-authored (Bilal/Claude only, never visitor input) — no XSS/multi-tenant risk; a malformed file only breaks that one post's own page |
| Expecting "push and it's live instantly" (true runtime, zero build) when GitHub Pages requires a rebuild | Medium | Low | Set expectations via spec `001`'s ~2-minute CI build+deploy target; this is a deploy-latency, not a manual-effort, tradeoff |
